# Make Video

프로젝트 루트는 `docs/`, `src/`, `CLAUDE.md`가 있는 디렉터리다. 아래 경로는 모두 그 루트 기준이다.
이 스킬은 요청한 `skills/make-video/SKILL.md`에 보관한다. 자동 검색 경로에 설치됐다고 전제하지 말고 CLAUDE.md의 시작 방법으로 직접 읽는다.
시작 전에 CLAUDE.md와 필요한 기준 문서를 읽는다. 값은 지시문에 복사하지 않고 원문 위치와 토큰으로 연결한다.

## 읽을 곳과 역할

| 필요 | 참조 |
|---|---|
| 색·폰트·원본 규격·재료 목록 | `docs/design.md` 1~4·6장 |
| 동작·의미 토큰·부품 적용·hold·카메라 | `docs/motion.md` 1~5장, 부품은 특히 3장 |
| 출력·텍스트·배경·폰·parts 외형 | `docs/video.md` 도입부와 1~5장 |
| 레퍼런스 분석 | `.codex/agents/art-director.toml` |
| 기획·장면표 | `.codex/agents/director.toml` |
| 실제 이미지·영상 구현 | `.codex/agents/builder.toml` |
| 독립 판정 | `.codex/agents/critic.toml` |

메인이 상태와 승인 기록을 소유한다. 역할은 순차 호출하고 critic은 제작자와 별도 실행한다.
native custom agent를 사용할 수 없으면 역할 정의를 읽은 별도 subagent로 실행한다. 메인이 역할극으로 독립 판정을 대체하지 않는다.
critic에는 필요한 결과·원본·기준만 전달하고 제작자의 자기평가로 판정을 유도하지 않는다.

## 0 준비와 재개

- `docs/`의 세 기준 문서, `src/screens/`, `src/parts/`, 필요한 폰트·에셋을 실제로 확인한다. 누락된 재료를 지어내지 않는다.
- 새 영상은 목적에서 안전한 폴더명을 정해 `run_dir = out/<영상이름>/`를 만든다. 기존 경로가 있으면 기존 작업인지 확인해 덮어쓰지 않는다.
- 재개는 `run_dir/state.json`과 실제 파일·해시·사용자 승인 메시지를 함께 확인한다. 기록만 있고 파일이 없으면 검증된 단계로 취급하지 않는다.
- state.json 필드: `stage`, `revisions`, `input_hashes`, `approvals`, `gate_failures`, `last_verdict`, `blocked_reason`.
- approvals에는 게이트, revision, 파일 해시, 사용자의 실제 선택·승인 메시지 근거를 기록한다. 침묵·critic PASS·다른 버전 승인은 승인이 아니다.
- 원본 docs/src와 이 하네스 파일은 제작 중 수정하지 않는다. 새 토큰이 필요하면 아래 새 후보 절차를 따른다.

## 1 BRIEF

“모션 만들자”로 시작하면 다음 세 질문을 한다. 이미 답한 내용은 재질문하지 않는다.
1. 무엇을 만들까요? 영상이 전달할 메시지와 목적을 받는다.
2. 몇 초로 만들까요? 이번 영상의 총 길이를 받는다.
3. 참고할 레퍼런스 URL은 무엇인가요? 여러 개면 원하는 역할도 함께 받는다.

답을 `run_dir/BRIEF.md`에 정리해 보여준다. BRIEF에 별도 승인 게이트를 추가하지 않고 다음 분석으로 진행한다.
BRIEF 총 길이는 사용자 입력으로 인정한다. 동작 수치의 새 후보 절차와 혼동하지 않는다.

## 2 레퍼런스 정리

art-director에 BRIEF와 원본 URL을 전달해 `run_dir/beat-sheet.md`를 만든다.
각 URL에 역할을 정하고 전체 뼈대 담당은 하나만 둔다. 불명확하면 역할 기본안을 제안하고 모호한 부분만 확인한다.
받은 원본·관찰 이미지는 `references/<레퍼런스이름>/`에만 저장하고 run_dir에는 링크와 관찰 기록을 둔다.
색·폰트·로고·새 UI는 레퍼런스에서 가져오지 않는다. 정확한 값이 미공개인 경우 원본 코드값이라고 주장하지 않는다.

### 반영률 규약

- 제작 전에 항목 ID, 담당 레퍼런스, 원본 시점, 역할, 관찰 내용, 확인 방법을 표로 고정한다.
- 구성·구도·카메라·전환·글자 배치 중 실제 참조하기로 한 항목을 분모 N으로 삼는다. 중복 항목은 한 번만 센다.
- 관찰되지 않은 역할은 근거와 함께 N/A로 구분한다. 항목을 잘게 쪼개거나 누락해 점수를 높이지 않는다.
- 대응 장면과 구현 증거가 확인된 항목만 M으로 센다. 기준 토큰으로 변환해도 역할과 동작 의도가 같으면 대응으로 인정한다.
- 반영률은 `100 × M / N`. 선택된 기획·스냅보드·영상마다 같은 항목 표로 다시 계산한다.
- 분모 변경은 사용자에게 이유를 보여주고 확정한 뒤 수행한다. N이 없거나 원본을 확인할 수 없으면 계산 불가로 멈춰 묻는다.

## 3 장면표 — 사람 게이트 1

director에 세 가지 기획 요약을 작성하게 하고 사용자에게 먼저 보여준다. critic 판정은 요약 아래 한 줄로 전달한다.
사용자가 한 안을 선택하면 해당 안만 상세화한다. 선택만 했다는 이유로 상세 장면표를 승인했다고 기록하지 않는다.
`run_dir/scenes.md`에 revision, 장면 ID·목적·프레임 구간·원본 경로·토큰 참조·배치 근거·반영 항목 ID를 적는다.
장면 구간과 총 길이는 BRIEF 및 기준 문서의 시간 토큰에서 계산하고 계산 근거를 남긴다.
상세 표를 먼저 보여준 뒤 critic의 현재 버전 판정을 한 줄 덧붙이고, 사용자의 명시적 승인을 기다린다.
PASS와 현재 상세 버전 승인이 모두 있어야 `approvals.scenes`를 기록하고 builder로 넘긴다. 이것이 첫 번째 사람 승인 게이트다.

## 4 스냅보드 — 사람 게이트 2

builder를 snap 모드로 호출한다. 결과는 `run_dir/video/`의 소스와 `run_dir/snap/`의 장면별 이미지·스냅보드다.
스냅보드가 모든 승인 장면을 포함하는지, 이미지가 실제 렌더된 것인지 메인이 확인한다.
스냅보드를 먼저 보여준 뒤 critic 판정을 한 줄 덧붙이고, 장면 ID로 피드백 또는 명시적 승인을 받는다.
PASS와 현재 스냅보드 승인이 모두 있어야 `approvals.snap`을 기록하고 영상 구현으로 넘어간다.
배치·외형 수정은 스냅보드를 갱신해 다시 확인받는다. 메시지·구성·장면 순서 수정이면 director부터 장면표 승인도 다시 받는다.

## 5 영상

장면표와 스냅보드의 승인·해시를 확인한 뒤 builder를 video 모드로 호출한다.
설치된 HyperFrames 스킬의 검사·실제 캡처·미리보기·렌더 절차를 따른다. 사용자 기준과 이 스킬의 두 승인 지점을 우선한다.
편집 가능한 HTML 미리보기를 보여주고 실제 프레임을 확인한 뒤 `run_dir/final.mp4`로 렌더한다. 추가 사람 승인 게이트는 만들지 않는다.
critic이 실제 영상·소스·인코딩 메타데이터로 최종 판정한다. 스냅보드 PASS를 영상 PASS로 재사용하지 않는다.
실제 수행한 검사만 완료로 기록하고, 최종 파일·미리보기·판정·남은 새 후보를 간단히 전달한다.

## 게이트와 실패 처리

기계 판정 게이트는 `scenes`, `snap`, `video`다. 사람의 승인은 scenes와 snap 두 곳에만 있다.
공통 통과 조건: **미등록 표현값 0 / 원본에 없는 UI 0 / 레퍼런스 반영률 60% 이상 / 필수 검증의 미확인 항목 없음**.
표현값은 동작 길이·곡선·색·크기 등 재사용하는 스타일·모션 값이다. 코드의 모든 숫자를 기계적으로 금지하는 규칙이 아니다.
기준값의 명시적 계산, BRIEF 총 길이, 시작·종료 시각, 콘텐츠 데이터는 각각 문서·입력·산식·원본 근거가 있으면 허용한다.
위치·정렬 및 video.md 4·5장이 레퍼런스에 위임한 정적 표시 크기는 원본 화면·부품과 참조 구도를 근거로 정했으면 통과한다.
이 예외로 새 모션 배율·이동량·곡선·폰트 크기를 우회해서 추가하지 않는다. 영상의 출력·가독성·외형 검증은 video.md를 따른다.
문구와 콘텐츠 데이터는 BRIEF·src의 실제 내용을 사용하고, 서체와 표시 스타일은 docs에서 가져온다.

판정 표시: `PASS|FAIL|BLOCKED <gate> <revision> — 미등록 n / 새 UI n / 반영 M/N=p% / 근거·미확인 요약`.
critic의 상세 근거는 메인이 `run_dir/review.md`에 기록하고 사용자에게는 먼저 보여준 결과 아래 이 한 줄만 붙인다.
FAIL이면 같은 gate의 실패 횟수를 state.json에 누적한다. 첫 불합격은 담당 역할이 원인만 수정하고 재검사한다.
같은 gate에서 두 번째 FAIL이면 자동 수정·다음 단계 진행을 멈추고 원인과 선택지를 사용자에게 묻는다. 파일명·revision·담당자 변경으로 횟수를 초기화하지 않는다.
BLOCKED도 진행하지 않고 필요한 근거나 재료를 묻는다. 다음 gate로 넘어가거나 기준을 낮춰 우회하지 않는다.
현재 gate를 통과한 뒤에만 해당 실패 횟수를 초기화한다. 사용자에게 명시적으로 재시작 지시를 받으면 그 근거를 기록한다.

### 변경과 새 후보

기준 문서·BRIEF·레퍼런스·사용한 src 원본이 달라지면 해당 입력과 연관된 장면표 및 후속 승인을 무효화한다. 장면표 변경은 후속 스냅보드 승인을 무효화한다.
새 값은 `run_dir/decisions.md`에 후보·출처·용도·기존 토큰으로 해결되지 않는 이유를 적어 묻고, 승인받아 해당 docs에 등록된 뒤 사용한다.
기준 문서를 몰래 바꿔 미등록 수치를 통과시키지 않는다. 수정된 기준과 승인 버전은 state.json의 입력 해시에도 반영한다.

## 실행 중 생기는 산출물

`run_dir/` 아래에 `BRIEF.md`, `beat-sheet.md`, `scenes.md`, `state.json`, `review.md`, 필요 시 `decisions.md`, `snap/`, `video/`, `final.mp4`를 둔다.
이 파일들은 실제 영상 제작 시 생긴다. 하네스만 설계하는 요청에서는 미리 만들거나 렌더를 시작하지 않는다.
